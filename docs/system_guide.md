# 시스템 안내서

> 문서 번호 BS-SYS-01 · 판 2 · 2026-10-22 · 적용: 말로 시키는 스펀지 블록 선별 로봇의 컴퓨터·모델·프로그램(젠북 노트북 한 대: Core Ultra 9 185H · Arc 내장 GPU · NPU 3720 · RAM 30GB · Ubuntu 24.04)
> 질문에 답할 때는 조항 번호로 인용한다(예: "시스템 안내서 3.4 에 따르면 …"). 숫자는 프로젝트 파일의 실측이고, 조항 끝 괄호가 출처 파일이다. 측정 조건(혼자·겹침·가짜 작업대)이 다르면 같은 항목도 값이 다르다.

## 1. 목적과 적용 범위

### 1.1 목적
이 안내서는 선별 로봇이 어떤 컴퓨터 장치에서 어떤 모델을 돌리는지, 왜 그렇게 나눴는지, 얼마나 빠르고 정확한지, 인터넷 없이 어떻게 도는지, 그동안 겪은 문제와 그래서 생긴 규칙, 말로 시킬 수 있는 명령 종류를 정리한다. 팔 다루는 법은 로봇 운용 설명서(BS-ROB-01), 블록 판정·처리 규칙은 작업 기준서(BS-STD-01)를 따른다.

### 1.2 적용 범위
젠북 노트북 한 대 안에서 도는 것에 적용한다: 모델 서버 OVMS(언어 모델·임베딩·리랭크·받아쓰기), 비전(YOLO), 음성 합성(TTS), 에이전트(LangGraph), 대시보드. 정책 학습을 하는 데스크톱(RTX 3060 Ti)은 학습 위치만 다룬다.

## 2. 전체 구성

### 2.1 말에서 동작까지
말로 시킨 명령은 이렇게 흐른다. 마이크 녹음 → 받아쓰기(Whisper, NPU) → 에이전트가 의도를 판별(임베딩 비교로 먼저, 애매하면 언어 모델 Qwen3) → 위 카메라로 블록을 셈(YOLO, NPU) → 학습한 정책으로 팔을 움직임(ACT, GPU) → 다시 셈 → 결과를 말함(음성 합성 Supertonic, CPU)과 대시보드 표시. 기준서·설명서 질문은 문서 검색(임베딩·리랭크) 뒤 언어 모델이 조항을 인용해 답한다. "멈춰"는 이 흐름을 거치지 않고 바로 정책을 끊는다. (CONTRACT.md 2·3절, agent/RESULT_20261021.md, ui/README.md)

### 2.2 프로그램과 주소
모델 서버는 OpenVINO Model Server(OVMS) 2026.4.1 이고 `127.0.0.1:8100` 에서 OpenAI 호환 주소(`/v3`)로 언어 모델·임베딩·리랭크·받아쓰기를 낸다. 대시보드는 `127.0.0.1:7870`, Physical AI Studio(녹화·정책 실행)는 `7860` 이다. 모두 이 노트북 안(127.0.0.1)에만 열려 있어 다른 PC 에서는 보이지 않는다. OVMS 는 재부팅하면 자동으로 뜨지 않으므로 `start_ovms.sh` 로 다시 띄운다. (SETUP.md 0·1·2절, ui/README.md 실행)

### 2.3 쓰는 모델
쓰는 모델은 이렇다: 언어 모델 Qwen3-4B(INT4), 임베딩 Qwen3-Embedding-0.6B(INT8), 리랭크 Qwen3-Reranker-0.6B(FP16), 받아쓰기 whisper-large-v3-turbo(INT8), 블록 검출 YOLOv8n 기반 5클래스(분홍·초록 정상·불량 4종 + 손, INT8), 음성 합성 Supertonic-3 한국어(목소리 10종), 팔 동작 ACT 정책 4개. 모델 파일은 전부 노트북 안(`models/`)에 있다. (SETUP.md 4절, vision/README.md, robot/README.md)

## 3. 장치 배치와 이유

### 3.1 장치 배치 한눈에
젠북에는 CPU·GPU(Arc 내장)·NPU 세 장치가 있고, 일을 이렇게 나눴다.

| 일 | 모델 | 장치 |
|---|---|---|
| 판단(의도·답·보고 문장) | Qwen3-4B | GPU |
| 문서 검색 순위 다시 매기기 | Qwen3-Reranker | GPU |
| 팔 동작 추론 | ACT 정책 | GPU |
| 받아쓰기 | Whisper | NPU |
| 블록 검출 | YOLO | NPU |
| 문서 검색 임베딩 | Qwen3-Embedding | CPU |
| 음성 합성 | Supertonic-3 | CPU |
| 정책 학습 | ACT | 데스크톱 RTX 3060 Ti |
| 블록 검출 학습 | YOLO | 젠북 GPU(xpu, 학습할 때만) |

(SETUP.md 0절, vision/README.md 학습 메모, robot/README.md 5.3, robot/policies.json)

### 3.2 언어 모델을 GPU 에, 4B 로 둔 이유
언어 모델은 GPU 에 Qwen3-4B 하나만 둔다. 4B 는 혼자 쓸 때 첫 토큰 0.133초, 초당 25.9토큰, 의도 JSON 5문장 5/5 였고, 8B 는 초당 13.9토큰, 5문장 3/5(개수 규칙 위반 2건), 메모리 약 2배(5.8GB 대 3.0GB)였다. GPU 에 언어 모델을 두 개 올렸을 때 GPU 가 멈추는 사고(GPU HANG)가 2번 나서, 한 서버에 언어 모델은 하나만 둔다. (SETUP.md 0·7.1절·8-3)

### 3.3 받아쓰기를 NPU 에 둔 이유
받아쓰기(Whisper)는 NPU 에 둔다. NPU 는 한 문장에 1.56~1.58초, GPU 는 0.90초로 GPU 가 빠르지만 받아쓰기 정확도는 같았다(CER 0.074, 완전 일치 4/6). GPU 는 언어 모델·리랭크·팔 정책이 같이 쓰므로, 받아쓰기를 NPU 로 빼 GPU 를 비워 둔다. NPU 판은 음성 길이와 거의 상관없이 약 1.5초 걸린다. (SETUP.md 0·3-6·7.3·7.6절)

### 3.4 YOLO 를 NPU 에 둔 이유
블록 검출(YOLO)도 NPU 에 둔다. 순수 추론 속도는 GPU 가 가장 빠르다(INT8 한 장 3.31ms, NPU 7.05ms, CPU 12.74ms). NPU 는 CPU 보다 1.8배 빠르다. NPU 에 둔 이유는 속도가 아니라 자리다: GPU 는 언어 모델이 쓰므로 비전을 NPU 에 두면 GPU 를 비워 둘 수 있다. 실제 카메라로 한 장을 셀 때(COCO 모델로 시험) NPU 처리는 19~22ms, 사진 찍기를 포함한 호출 전체는 0.74~0.76초였다. (vision/bench_results.md, vision/README.md "장치별 속도"·"10-21 검증 결과")

### 3.5 임베딩과 음성 합성을 CPU 에 둔 이유
문서 검색 임베딩은 CPU 에서도 질문 한 문장에 25~58ms 로 충분히 빠르다. 임베딩·리랭크를 NPU 에 올리려던 시도는 컴파일 중 메모리가 12.6GB 까지 늘어 실패해 접었다. 음성 합성(Supertonic-3)은 CPU 에서 돌고, 스레드를 4개로 정해야 짧은 문장이 0.86초다(기본 자동 스레드는 2.15초로 오히려 느림). (SETUP.md 0·6·7.2·7.4절·8-6)

### 3.6 리랭크를 GPU 로 옮긴 이유
리랭크는 처음 계획(CPU)과 달리 GPU 로 옮겼다. CPU 에서는 문서 8개에 5.8초, GPU 에서는 0.36~0.44초였고 순위는 같았다. 리랭크 위치가 질문 응답 시간에 크다: CPU 로 돌아가면 질문 하나에 약 4초가 늘어난다. 리랭크는 Qwen3 지시 템플릿을 붙여야 순위가 맞는다(원문 그대로면 엉뚱한 문서가 0.91 로 1위). (SETUP.md 0·3-5·7.2절, agent/RESULT_20261021.md 2절)

### 3.7 학습은 어디서 하나
정책(ACT) 학습은 데스크톱의 RTX 3060 Ti 원격 트레이너에서 한다: 10-20 실측 초당 5.76~7.49 스텝, 50 에피소드·10 에포크면 에피소드 20초 기준 정책당 약 1시간 42분(추정), 확정한 15초 에피소드면 약 1시간 18분(계산). 젠북 Intel GPU 로는 초당 1.1 스텝이라 같은 학습에 8시간 반이 걸려 쓰지 않는다. 블록 검출(YOLO) 학습은 젠북 GPU(xpu)에서 한다: 합성 사진 150장·50에포크에 학습 9.7분(10-21 밤, 합성 공 사진으로 경로 시험). 검증 점수는 CPU 로 다시 낸다 — xpu 에서 검증하면 후보가 잘려 점수가 가짜로 낮게 나온다(같은 모델 mAP50 xpu 0.091, CPU 0.995). (robot/README.md 5.3·"재개", docs/recording_guide.md 1절, vision/README.md 학습 메모·"10-21 밤")

## 4. 실측

### 4.1 응답 시간
가짜 작업대(정책 1회 0.3초)로 잰 응답 시간: 작업 명령(불량·분홍·초록·손 전달)의 첫 대답 0.08초, 결과 보고 2.46초, 기준서 질문 1.59초(세 문서로 넓히기 전, 지금 값은 4.3), "멈춰" 0.00초(10-21 22:51~22:56, 받아쓰기·음성 합성 시간 제외). 실제로는 앞에 받아쓰기 약 1.6초가 붙고, 실제 로봇이면 정책 실행 시간과 카메라 촬영 시간이 더해진다. (agent/RESULT_20261021.md 3·5절)

### 4.2 의도 판별 정확도
의도 판별은 시험 문장 87개(의도 9종) 모두 맞았다(87/87). 임베딩 비교로 확정한 42건은 평균 49ms, 언어 모델로 넘긴 36건은 평균 0.64초였다. 받아쓰기 흔들림·동의어 문장(죠·블럭·핑크·녹색·연두) 15개도 15/15. (agent/RESULT_20261021.md 5절)

### 4.3 문서 질문 정확도와 시간
문서 검색은 작업 기준서·로봇 운용 설명서·시스템 안내서 세 문서(99조각)에서 한다. 세 문서 질문 47문항에서 정답 문서·조항이 상위 3개에 든 것이 42/42, 답이 정답 조항을 인용한 것이 39/42, 문서 밖 질문 거르기가 5/5였다. 질문 하나에 판별 → 검색 → 답까지 중앙 3.13초, 최대 6.81초(답이 긴 나열일 때)였다(10-22 새벽). 처음 기준서 하나일 때는 질문 하나에 약 10초 걸렸는데, 리랭크를 GPU 로 옮기고 확실할 때 리랭크를 건너뛰고 답을 한 문장으로 줄여 빨라졌다. 세 문서로 넓히면서 조각이 길어져 약 0.9초 느려졌다. 안전 수칙(6장)은 언어 모델이 뜻을 뒤집은 적이 있어 기준서 문장을 그대로 읽는다. (agent/RESULT_20261021.md 2·5·7절)

### 4.4 배치 질문과 여러 단계 명령
배치 질문(scene) 시험 8개는 8/8(답의 숫자·칸이 카메라 결과와 맞음, 로봇 0회), 중앙 1.60초였다. 여러 단계 명령(plan) 시험 10개는 10/10(끝난 작업대가 기대와 같음, 거절 3건은 로봇 0회)이고, 계획을 말하기까지 중앙 3.68초, 할 수 없는 요청 거절은 0.65~0.69초였다. (agent/RESULT_20261021.md 5절)

### 4.5 받아쓰기 정확도
합성 음성(목소리 F1·M1)으로 시연 문장 12개를 받아쓰면 Whisper 원문이 24개 중 18개 정확히 맞았고, 프로그램이 잦은 오인식을 바로잡은 뒤에는 24/24 였다. 틀린 것은 모두 소리가 같은 말이다: "불량"과 "분량"은 둘 다 [불량]으로 소리 나고, "작업대"는 [작업때]라 "작업 때"로 적힌다. 서버 왕복은 약 1.6~1.8초. 받아쓰기에 문맥(prompt)을 주는 기능은 지금 서버(NPU)가 무시한다(CPU 로 직접 돌리면 18/24 → 23/24 지만 한 번에 약 5초). 사람 목소리는 아직 재지 않았다. (docs/stt_check.md, docs/stt_prompt_check.md, ui/README.md "10-21 밤 3·4")

### 4.6 NPU 를 같이 쓸 때
받아쓰기(NPU)·블록 검출(NPU, 초당 10장)·언어 모델(GPU)을 동시에 돌려도 실패 0 이었다. 받아쓰기는 1.56 → 2.22초, 검출은 13.7 → 27.4ms, 언어 모델은 초당 29.1 → 27.6토큰으로 조금씩 느려졌다. 받아쓰기를 가장 늦추는 것은 NPU 가 아니라 언어 모델(+30%)이었다. 검출을 최대 속도로 돌리면 받아쓰기가 더 느려지므로 비전 미리보기는 NPU 초당 10장 이하로 묶는다. (SETUP.md 7.6)

### 4.7 언어 모델 캐시(KV 캐시)
언어 모델의 KV 캐시를 1GB 로 고정했다. 원래 설정(필요한 만큼만 잡는 동적 캐시)에서는 보고·답 뒤에 의도 판별의 앞부분 캐시가 밀려나 판별이 1.60초 걸렸는데, 1GB 고정 뒤 0.63초가 됐다. 판별 결과는 같고, 대가는 메모리 약 1.3GB 다. (SETUP.md 0·7.7절)

### 4.8 메모리
권장 구성(4B·임베딩·리랭크 GPU·Whisper NPU)에 부하를 준 뒤 `free -g` 기준 사용 14GB·가용 16GB 였다. KV 캐시 1GB 고정 뒤 시연 당일 여유는 약 11GB 로 추정한다. NPU·GPU 가 쓰는 메모리도 시스템 RAM 에서 나간다. 비전 학습(xpu)은 약 13GB 를 써서 시연 중에는 하지 않는다. OVMS 는 메모리 상한(기동 때 가용 − 3GB)을 두어, 모자라면 OVMS 만 죽고 다른 프로그램은 안전하다. (SETUP.md 0·1·7.5절)

### 4.9 블록 검출 정확도
블록 검출은 아직 합성 사진으로만 검증했다. 학습 경로 시험(합성 공 사진 150장으로 학습)의 CPU 검증은 정밀도 0.997, 재현율 1.0, mAP50 0.995 였다. 자동 라벨은 흩어 놓은 파스텔 블록에서 정밀도 0.996, 재현율 1.000(보정 10장 뒤), 몰아 놓아 맞닿은 블록에서 0.960 / 0.997 이었다. 실물 사진 촬영·학습은 10-22 에 하므로 실물 정확도는 아직 없다. (vision/README.md 자동 라벨 정확도·"10-21 밤")

## 5. 인터넷 없이 돌기

### 5.1 외부 API 를 쓰지 않는다
선별 로봇은 인터넷 없이 돈다. 언어 모델·임베딩·리랭크·받아쓰기·음성 합성·블록 검출이 모두 이 노트북 안에서 돌고, 외부 API 는 하나도 부르지 않는다. 결과 보고서의 "외부 API 호출 0건" 표시는 대시보드가 실제로 막은 외부 접속이 0건일 때만 나온다. (SETUP.md 머리말, ui/README.md 오프라인)

### 5.2 서버 쪽에서 막은 것
모델 서버(OVMS)는 기동에 인터넷이 필요 없고, 서버 안의 모델 내려받기 기능이 혹시 불려도 닫힌 로컬 포트로 가서 바로 실패한다(시험 0.08초). 대시보드는 자기 프로세스(같이 도는 에이전트 포함)의 바깥 연결을 모두 즉시 실패시키는 장치(`ui/netguard.py`)를 걸어, 와이파이가 켜져 있어도 끈 것과 같이 동작한다. 막은 건수는 화면 맨 위 "외부 접속 0건"에 보인다. (SETUP.md 1·11절, ui/README.md 오프라인)

### 5.3 꺼 둔 사용 통계(텔레메트리)
라이브러리들이 몰래 보내는 사용 통계·내려받기를 껐다: Gradio 분석·버전 확인, Hugging Face 온라인 접속·통계, Supertonic 모델 자동 내려받기, Chroma 사용 통계, LangSmith 추적, 임베딩 사전(tiktoken) 내려받기, Ultralytics(YOLO)의 DNS 확인·검출마다 보내는 통계(`YOLO_OFFLINE=1`). 실행 중 자동 패키지 설치도 꺼져 있다. (SETUP.md 11절, vision/detect.py, ui/README.md 오프라인)

### 5.4 화면(브라우저) 쪽
대시보드 화면은 시스템 글꼴만 쓰고 외부 글꼴·CDN 을 부르지 않는다. 크롬을 바깥 이름 풀이를 막은 상태로 띄워 명령 전체를 돌렸을 때 외부 요청 0건, 화면 오류 0건이었다. 결과 보고서 HTML 은 사진까지 파일 안에 담아 외부 링크가 없다. 와이파이를 실제로 끄고 해 본 시험은 아직 없다. (ui/README.md 오프라인, SETUP.md 11절)

## 6. 겪은 문제와 규칙

### 6.1 GPU 가 멈춘 사고(GPU HANG)
GPU 가 멈추는 사고가 세 번 있었다. ① 10-21 16:48, ② 17:20 — 언어 모델 두 개(8B·4B)를 한 서버에 올린 상태에서 GPU 오류로 OVMS 가 죽었다. ③ 20:22~20:33 — 비전의 YOLO 학습(PyTorch xpu)이 GPU 를 같이 쓰자 언어 모델이 7분 동안 응답 없이 멈췄다가 20:29:37 GPU HANG 으로 OVMS 가 죽었다(학습은 무사). 그래서 규칙이 둘 생겼다: 서버에 언어 모델은 하나만, 젠북 GPU 는 한 번에 한 작업(xpu 학습은 OVMS 를 내린 뒤에만, 측정·시연·리허설 중 금지). OpenVINO 끼리(YOLO GPU 초당 30장 + 언어 모델 + 받아쓰기 3분)는 실패 0 이었다. (SETUP.md 8-3·8-13·7.6, CONTRACT.md 5절)

### 6.2 메모리 부족 사고
10-21 16:37 8B 모델을 추가하다 시스템 메모리가 모자라 다른 프로그램이 스왑으로 밀렸다(죽은 프로그램은 없음). 그 뒤 OVMS 메모리 상한을 "기동 때 가용 메모리 − 3GB"로 자동 계산하고, 메모리가 모자라면 OVMS 가 먼저 죽게 했다. (SETUP.md 8-1·1절)

### 6.3 언어 모델의 생각 모드
Qwen3 는 기본으로 답하기 전에 300~400토큰을 먼저 "생각"해서 답이 16~37초 걸렸다. 그래서 모든 요청에서 생각 모드를 끈다(`enable_thinking: false`). (SETUP.md 3-1·8-10)

### 6.4 여러 작업이 같이 쓰면 느려진다
언어 모델은 여러 요청을 섞어 처리하므로, 다른 평가와 겹쳤을 때 4B 가 초당 25.9 → 8.2토큰까지 떨어졌다. 시연 중에는 다른 평가·측정을 돌리지 않는다. (SETUP.md 3-7)

### 6.5 받아쓰기의 같은 소리 말
Whisper 는 "불량 몇 개"를 "분량 몇 개"로, "작업대"를 "작업 때"로 적는다(두 목소리 모두). 소리가 같은 말이라서다. 대시보드의 받아쓰기는 이런 말을 바로잡는 표(분량 → 불량, 작업 때 → 작업대, 골라내죠 → 골라내 줘)를 거치고, 로그에 원문을 같이 남긴다. 말할 때는 "불량품 몇 개 남았어?", "지금 작업대 상태 어때?"처럼 말하면 원문부터 맞았다. (ui/README.md "10-21 밤 3", docs/stt_check.md)

### 6.6 정책 학습 중 Stop 금지
Studio 학습 화면의 Stop 확인창은 "체크포인트를 저장한다"고 하지만 사실이 아니다. 원격 학습에서 Stop 을 누르면 트레이너가 학습을 취소하고 모델을 보내지 않아 모델 목록에 아무것도 생기지 않는다(10-20 사례). 줄이고 싶으면 보낼 때 에포크를 작게 정한다. (robot/README.md 5.4)

### 6.7 처음 켤 때 느림
Whisper 를 NPU 에 처음 올릴 때는 컴파일에 약 3분 25초가 걸린다. 한 번 컴파일한 뒤에는 캐시 덕에 5초다. YOLO 도 새 프로그램의 첫 검출은 캐시가 없으면 8.1초, 있으면 2.3초다. OVMS 는 죽어도 자동으로 다시 뜨지 않는다. (SETUP.md 1·8-9, vision/README.md "10-21 검증 결과")

## 7. 명령 종류

### 7.1 작업 명령
팔을 움직이는 작업 명령은 네 가지다. 불량 골라내기("불량품 골라내 줘"), 분홍 옮기기("분홍 블록 옮겨 줘"), 초록 옮기기("초록 블록 옮겨 줘"), 손에 건네기("분홍 블록 하나 내 손에 줘"). 개수를 말하면("두 개만") 그만큼, 안 말하면 투입 구역에 그 블록이 0개가 될 때까지 반복한다. 분홍은 "핑크", 초록은 "녹색"·"연두", 블록은 "블럭"이라고 해도 같다. (CONTRACT.md 2절, docs/intents.csv)

### 7.2 결과 보고·질문·멈춤
팔을 움직이지 않는 명령은 셋이다. "결과 알려 줘"(결과 보고: 카메라로 다시 세어 기록과 대조하고 말과 보고서로 알림), 기준서·설명서·안내서에 대한 질문(문서 검색 뒤 조항을 인용해 답함, 문서에 없으면 없다고 함), "멈춰"(언어 모델을 거치지 않고 바로 정책을 끊음). (CONTRACT.md 2절, agent/RESULT_20261021.md 2절)

### 7.3 배치 질문(scene)
"지금 작업대 어때?", "분홍 블록 어디 있어?", "불량 몇 개 남았어?" 같은 지금 배치·개수·위치 질문은 위 카메라로 한 장 찍어 답하고 로봇은 움직이지 않는다. 답의 숫자와 칸 이름은 프로그램이 카메라 결과와 맞는지 검사한 뒤에 말한다. (CONTRACT.md 3절 agent, agent/RESULT_20261021.md 5절)

### 7.4 여러 단계 명령(plan)
"분홍 두 개만 옮기고 불량 골라내 줘", "불량 빼고 나머지 다 정리해 줘"처럼 배운 동작 4개를 순서·개수·조건으로 엮은 처음 듣는 명령은, 언어 모델이 단계 목록을 세우고 프로그램이 검증한 뒤 "순서대로 할게요. 1) … 2) …"라고 알리고 단계마다 카메라로 확인하며 실행한다. 숫자가 아닌 모양 만들기·쌓기·줄 세우기, 다른 색 그릇에 넣기, 초록을 손에 주기처럼 배운 적 없는 동작은 실행 전에 거절한다. 한 단계가 실패하거나 멈추면 남은 단계는 하지 않는다. (agent/RESULT_20261021.md 5절)

### 7.5 숫자 모양 만들기(좌표 집기)
"분홍 블록으로 7 만들어 줘" 같은 숫자 모양 배치는 좌표 집기 기능으로 한다. 에이전트 연결은 10-22 에 끝났다. 계획을 세워 "숫자 7: 블록 7개, 약 3분 걸립니다. 할까요?"라고 묻고, "응"이라고 해야만 실행한다. "아니"면 끝나고, "멈춰"는 언제든 된다. 숫자가 아닌 모양(하트·별·동그라미), 두 자리 숫자, 블록 부족, 팔이 닿지 않는 자리는 이유를 말하고 거절한다. 보정 전에는 "보정 전이라 계획만 보여 드릴게요"라고 말하고 확인을 묻지 않으며, 대시보드 현재 배치 칸에 칸 배치(목표 칸의 놓는 순서 번호와 어느 블록에서 오는지)를 보여 준다. 지금은 보정 전이라 계획만 보여 주고, 실제 팔에 보낸 적은 아직 없다(송신 0회). 실제 구동은 입회 보정 뒤에 한다. (agent/README.md "좌표 집기(arrange)", agent/RESULT_20261021.md 6절, robot/COORD_PICK.md 7·9절)

### 7.6 시연 순서
본 시연은 투입 구역의 블록 4개(정상 분홍 2·정상 초록 1·불량 1)로 다섯 마디를 차례로 말한다: ① "불량품 골라내 줘" ② "지금 배치 어때?" ③ "불량 빼고 나머지 다 정리해 줘" ④ "분홍 블록 하나 내 손에 줘" ⑤ "결과 알려 줘". ②는 배치 질문, ③은 여러 단계 명령(분홍 2개 옮기기 → 초록 1개 옮기기)이다. (docs/standard.md 2.4, docs/recording_guide.md 1절)
