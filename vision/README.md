# vision — 위 카메라 → 블록 검출(OpenVINO NPU) → 구역별 개수

계약서 3절 `detect_objects()` 를 만드는 계층이다. 2026-10-21 에 도구·자동 라벨·검수 화면·학습 파이프라인을 만들고 합성 데이터로 끝까지 검증했다. 실제 사진 촬영·검수·학습은 2026-10-22 에 한다. **내일 칠 명령 순서는 맨 끝 "재개" 절**에 있다. 10-22 아침 위 카메라 실측(노출 200·색온도 4600K, 5000K 이상 금지)과 autolabel 의 구역 밖 블록 후보 버리기를 반영했다(맨 끝 "10-22 아침"). 10-22 점심에 방법 B 첫 묶음(`rec`, 97장) 초안을 사람 검수 직전까지 만들었다(맨 끝 "10-22 점심").

**물체 변경 (10-21 밤, 사용자 결정):**
- 부직포볼 대신 스펀지 수세미를 깍둑썬 약 3cm 블록을 쓴다. 거친 초록 층은 뗐다.
- **색은 파스텔 분홍·초록**이다(10-21 밤 두 번째 변경, 빨강·파랑 → 분홍·초록). 흰 무광 식탁보 위에 놓는다. 말 동의어: 분홍 = 핑크, 초록 = 녹색 = 연두.
- 불량은 굵은 검정 유성매직 X 를 6면 전부에 칠한 블록이다.
- 개수: 정상 분홍 8, 정상 초록 8, 불량 분홍 2, 불량 초록 2, 여유분.
- 예비 물체는 흰 매직블럭(멜라민) 3cm 21개다.
- 코드 식별자는 그대로 둔다. 사람이 보는 글만 블록·분홍·초록으로 바꿨다.
  - 클래스: `red_*` = 분홍, `blue_*` = 초록
  - 구역: `bowl_red` = 분홍 그릇, `bowl_blue` = 초록 그릇
  - 그 밖에 모델 폴더 `ball_int8_openvino_model`, 환경변수 `BALL_*`, 자동 라벨 설정 키 `red`·`blue`

## 카메라

- 위 카메라는 Studio 의 `front` 카메라(ZVCAI USB_Camera, serial `zvcai231100001`)이고 경로는 `/dev/v4l/by-id/usb-ZVCAI_USB_Camera_zvcai231100001-video-index0` 이다. 10-21 엔 `/dev/video2`, 10-22 엔 `/dev/video0` 이었다. 꽂는 순서에 따라 번호가 바뀌므로 by-id 경로를 쓴다. `gripper` 카메라는 icSpring 이다.
- **카메라는 더 못 숙인다**(10-22 사용자 확인). 화면 위쪽 약 25% 는 의자·바닥이고, 아래쪽에 로봇 몸체(흰 3D 프린트)와 왼쪽 아래 흰 접시 일부가 들어온다. 흰 부품은 4600K 에서도 초록 마스크에 넓게 걸린다. 그래서 autolabel 이 5구역 밖 블록 후보를 버린다(아래 "autolabel.py 규칙").
- **Studio 가 카메라를 잡고 있는 경우가 많다.** Studio 안의 `physicalai.capture.transport._publisher_worker` 가 front·gripper 를 계속 열어 둔다(10-21 13:05 부터 확인). 구독자(미리보기 화면 등)가 없어지면 런타임이 45초, publisher 가 5초 뒤에 놓는다.
- `source="auto"`(기본)의 동작:
  - 장치가 비어 있으면 직접 연다. 찍고 나면 바로 닫는다.
  - Studio 가 잡고 있으면 **장치를 열지 않는다.** Studio 미리보기와 같은 웹소켓(`/api/cameras/ws`)에 구독자로 붙어 한 장만 받는다. Studio 에 등록된 카메라 설정을 GET 으로 읽어 그대로 보내므로 Studio 설정은 바뀌지 않는다. 받는 프레임은 JPEG q80 이다.
  - Studio 가 아닌 프로세스가 잡고 있으면 `CameraBusy` 를 낸다.
- `source="device"` 를 주면 장치만 쓰고, 장치가 바쁘면 실패한다.
- ⚠ **사용 여부 확인에 `fuser`·`lsof` 를 쓰면 안 된다.** Studio 는 privileged 컨테이너라서 `/dev` 가 따로 있다. 같은 장치라도 경로와 inode 가 달라서 두 도구 모두 "아무도 안 씀"이라고 답한다(10-21 실측). `camera.busy_pids()` 는 `sudo -n` 으로 모든 프로세스의 열린 fd 를 stat 하고 장치 번호(rdev)로 비교한다.

```
$PY vision/camera.py --busy          # [] = 비어 있음, [PID] = 사용 중
$PY vision/camera.py --snap /tmp/x.jpg
```

### 자동 노출·자동 화이트밸런스·60Hz 고정

색으로 분홍과 초록을 가르므로, 촬영(학습) 때와 시연(추론) 때 노출과 색온도가 같아야 한다. 파스텔은 채도가 낮아서 노출이 높으면 흰색으로 날아간다(아래 "노출 점검"). 설정한 값은 USB 를 다시 꽂거나 재부팅할 때까지 카메라에 남는다. Studio 는 노출 컨트롤을 건드리지 않는다. **Studio 미리보기를 닫아 카메라가 빈 상태에서** 설정한다. `v4l2-ctl` 은 10-21 에 설치됐다(v4l-utils 1.26.1, 총괄 세션).

```
CAM=/dev/v4l/by-id/usb-ZVCAI_USB_Camera_zvcai231100001-video-index0
v4l2-ctl -d $CAM --list-ctrls
v4l2-ctl -d $CAM -c auto_exposure=1,exposure_dynamic_framerate=0,white_balance_automatic=0,focus_automatic_continuous=0,power_line_frequency=2
v4l2-ctl -d $CAM -c exposure_time_absolute=200,white_balance_temperature=4600,focus_absolute=130
```

- 첫 줄 `-c` 는 자동 모드를 끄고 60Hz 로 바꾼다. 둘째 줄은 값을 넣는다. 자동 모드가 켜져 있으면 값 컨트롤이 inactive 라 먹지 않으므로 반드시 첫 줄 다음에 실행한다.
- `auto_exposure` 는 메뉴형이다: 1 = Manual, 3 = Aperture Priority(자동, 기본값).
- `exposure_time_absolute` 단위는 100µs 다. 200 = 20ms 이고 30fps(33ms) 안에 들어간다. 333 을 넘기면 30fps 가 깨진다.
- **위 숫자는 10-22 10:13 교육장 실제 조명에서 정한 값이다**(총괄 실측): 노출 200, 색온도 4600K, 초점 130, 채도(`saturation`) 64 는 기본값 그대로. 10-21 의 166 은 자동 모드가 잡아 둔 값이었다.
  - 노출: 240 이면 포화 픽셀이 10.75% 라서 200 으로 정했다.
  - **색온도 5000K 이상은 쓰지 않는다.** 이 조명은 초록 기운이 있어서, 5000K 부터 흰 식탁보가 통째로 초록(`blue_*`) 마스크에 걸린다(5000K 에서 초록 픽셀 약 6.6만). 4600K 는 식탁보가 살짝 푸르게 찍히지만 색상이 초록 범위(기본 30~90) 밖이다.

  | 색온도(노출 200) | 식탁보 RGB | 식탁보 색상 H · 채도 S (RGB 에서 계산) | `--exposure` 의 가장 큰 초록 덩어리(화면 가운데 대비) |
  |---|---|---|---:|
  | 4600K | 171, 206, 219 | 98 · 56 (초록 범위 밖) | 3% |
  | 5000K | 179, 210, 208 | 88 · 38 (초록 범위 안) | 28% |
  | 5400K | 185, 214, 194 | 69 · 35 (초록 범위 안) | 44% |

  - 4600K 의 식탁보는 채도(56)가 실물 파스텔 블록(분홍 약 45)보다 높다. 그래서 노출 점검과 보정을 채도가 아니라 영역·색 차이로 하게 고쳤다(아래 "노출 점검", "실물 첫 10장으로 임계값 맞추기").
  - 보정(재개 3단계)이 실물 초록 블록으로 초록 색상 범위를 다시 잡는다. 상한이 98 근처까지 올라가면 4600K 에서도 식탁보가 걸린다. 그때는 보정이 "구역 안 배경의 x% 가 이 색 범위에 걸려" 경고를 낸다. <!-- TODO: 확인 필요 --> 색온도를 300 내리면(4300K) 식탁보가 더 푸르게 찍혀 초록에서 멀어질 것으로 본다. 다만 블록 색도 같이 움직이니 보정을 다시 한다.
- 이 카메라는 자동 초점도 있다. 초점이 흔들리면 박스도 흔들리므로 같이 고정한다.
- 전원 주파수가 50Hz(`power_line_frequency=1`)로 잡혀 있었다. 한국은 60Hz 라 형광등 아래에서 줄무늬·깜빡임이 생길 수 있어 `power_line_frequency=2`(60Hz)로 바꾼다.
- 원래대로 되돌리기: `-c auto_exposure=3,white_balance_automatic=1,focus_automatic_continuous=1`

v4l2-ctl 없이 같은 일을 하는 명령(같은 컨트롤 이름, 적은 순서대로 설정):

```
$PY vision/camera.py --list
$PY vision/camera.py --set auto_exposure=1 exposure_dynamic_framerate=0 white_balance_automatic=0 focus_automatic_continuous=0 power_line_frequency=2 exposure_time_absolute=200 white_balance_temperature=4600 focus_absolute=130
```

### 노출 점검 (파스텔)

```
$PY vision/camera.py --snap /tmp/cam_test.jpg && $PY vision/autolabel.py --exposure /tmp/cam_test.jpg
```

블록 몇 개를 흰 식탁보 위 화면 가운데에 두고 찍어서 아래 값을 본다. 식탁보 영역은 `zones.json` 이 있으면 input 구역, 없으면 화면 가운데 절반(가로·세로 25~75%)이다. 출력의 `region` 이 어느 쪽인지 알려 준다.

| 값 | 뜻 | 좋음 |
|---|---|---|
| `table_v` | 식탁보 밝기(식탁보 영역에서 채도 80 미만·밝기 120 초과 픽셀의 V 중앙값) | 200~250 |
| `clip_pct` | 포화 픽셀 비율(화면 전체, 어느 채널이든 250 이상) | 5% 미만 |
| `obj_s` | 블록 채도(식탁보 영역에서 분홍·초록으로 잡힌 픽셀의 S 중앙값) | 40 이상 |
| `blob_pct` | 색별로 가장 큰 덩어리가 **화면 가운데 절반**에서 차지하는 %. 색온도는 식탁보 전체의 일이라 구역과 상관없이 여기서 잰다. 10:42 `zones.json` 의 input 은 약 1만 px 로 작아서, 거기서 재면 블록 두어 개로도 10% 를 넘는다 | 10% 미만 |

- 판정 순서: 식탁보가 초록·분홍으로 잡힘(`blob_pct` 10 이상) → 밝다 → 어둡다 → 블록이 안 보임(`obj_px` 300 미만) → 블록 채도 낮음 → 좋음.
- "밝다"면 `exposure_time_absolute` 를 20% 내리고(200 → 160) 다시 찍는다. "어둡다"면 20% 올린다(333 이하). "식탁보가 초록으로 잡힌다"면 `white_balance_temperature` 를 300 내린다.
- **10-22 실물로 고친 점**

### autolabel.py 규칙

- **색**: 분홍(`red`)과 초록(`blue`) HSV 범위로 마스크를 만든다.
  - 기본값(보정 전): 분홍 색상 125~179 또는 0~4, 초록 색상 30~90, 둘 다 채도 35 이상·밝기 80 이상.
  - 분홍 125 는 10-22 실물 값이다. 실물 분홍 스펀지(4600K)는 색상 중앙값 148, 하위 5% 119 로 자홍 쪽이다. 예전 150 은 블록 픽셀의 1/3 만 잡아, 녹화 사진에서 분홍 블록이 박스 2개로 쪼개지거나 통째로 빠졌다. 푸른 식탁보(색상 98~100)는 안 걸린다.
  - 파스텔은 채도가 낮다. 합성 기준 분홍 H 167~169 · S 59~123, 초록 H 47~51 · S 58~129 이고, 흰 식탁보는 채도 99.9% 가 17 이하다.
  - 이전 진한 빨강·파랑 규칙은 `--colors strong` 으로 남겼다(합성 비교용).
- **블록**: 분홍/초록 마스크 덩어리를 찾고 볼록 껍질로 박스를 친다. 박스는 옆면까지 보이는 블록 전체를 덮는다.
  - 덩어리가 블록 하나인지는 모양으로 본다. 볼록도 0.88 이상이고 최소 회전 사각형의 가로세로비가 1.6 이하이면 하나다. 화면 가장자리에서는 옆면이 보여 1.5 쯤까지 늘어난다. 볼록도 0.92 미만이거나 가로세로비 1.4 초과면 `irregular` 표시를 붙인다.
    - 이 네 값은 설정 `shape`(`solid_min` `aspect_max` `solid_odd` `aspect_odd`)이다. 기본값은 합성(위에서 본 블록) 기준이다.
    - 10-22 실물 카메라는 비스듬해 윗면과 앞면이 같이 보인다. 녹화 사진의 블록 하나 크기 덩어리 298개는 가로세로비 중앙값 1.52, 볼록도 중앙값 0.91 이라 거의 모두 `irregular` 가 된다. 보정(`--calibrate`)이 검수한 블록으로 다시 잰다.
  - 아니면 맞닿은 블록으로 보고, 면적을 블록 하나 면적으로 나눠 개수를 어림한 뒤 픽셀 좌표 k-means 로 나눈다. 블록 하나 면적은 `obj_area_px` 이고, 없으면 그 사진에서 모양이 맞는 덩어리 면적의 중앙값을 **두 색을 합쳐** 쓴다(10-22). 한 색에 모양이 맞는 덩어리가 없을 때 예전에는 그 색 덩어리를 전부 둘로 잘랐다. 블록 크기를 아예 모르면 자르지 않고 `irregular` 로 검수에 보낸다.
  - 나눈 조각이 블록 모양·크기가 아니거나 블록 사이 빈 곳까지 덮으면 `split` 표시를 붙인다.
  - 모양은 어긋나도 면적이 블록 하나쯤이면 나누지 않고 `irregular` 로 검수에 보낸다(원근으로 길쭉해진 블록).
- **불량**: 블록 안쪽(가장자리 15% 깎음)에서 마커 픽셀이 `defect_ratio`(기본 5%) 이상이면 불량이다. 2.5~8% 구간이면 `defect?` 표시를 붙인다.
  - 검정 마커는 HSV 밝기 70 이하이면서 **그 블록 밝기(중앙값)의 0.45배보다 어두운** 픽셀만 센다(`black_rel`). 그늘진 옆면이나 스펀지 기공이 마커로 세지는 것을 막는다.
  - 채도로는 거를 수 없다. JPEG 압축 때문에 검정 X 의 채도가 높게 나와서, 채도 상한을 두면 진짜 X 까지 놓친다(10-21 밤 시험).
  - 마커 색은 `--marker black|white|yellow` 또는 `H,S,V,H,S,V` 로 바꿀 수 있다. 결정된 것은 검정이다.
- **손**: **사람이 review.py 에서 그린다**(10-21 확정).
  - 기본(`--hands hint`)은 피부색 덩어리를 `hand?` 제안 박스로만 넣고, 그 사진을 검수로 보낸다. 피부색 조건은 YCrCb, 채도 40 이상, 색상 0~25 또는 172~179 다.
  - **분홍 스펀지는 YCrCb 로는 피부색과 같다.** 그래서 색상 조건을 더했다(합성 분홍 H 167~169, 손 H 10~11).
  - 분홍이 연어색(색상 0~10)이면 손과 색상이 겹친다. 보정이 손 피부 픽셀의 20% 넘게 분홍 범위에 들면 경고한다.
  - `zones.json` 이 있으면 `hand_spot` 에 걸친 덩어리만 제안한다. 화면 1/3 이 넘는 덩어리는 작업대·조명 색으로 보고 버린다.
- **구역 밖 버리기**(10-22): `zones.json` 이 있으면 5구역(input·bowl_red·bowl_blue·bowl_defect·hand_spot) 어디에도 중심이 없는 블록 후보를 버린다. 화면에 의자·바닥·로봇 몸체·접시가 들어오고, 흰 부품이 초록 마스크에 걸리기 때문이다(위 "카메라"). 기본으로 켜져 있고 `--keep-outside` 로 끈다.
  - 블록 크기 덩어리는 박스 중심으로 판정한다. 중심이 구역 밖 10px(`zone_tol_px`) 안이면 남긴다. 반쯤 걸친 블록이 박스 중심 몇 px 차이로 빠지지 않게 하려는 것이다.
  - 블록 2개 이상 크기 덩어리는 픽셀이 절반 넘게 구역 밖이면 버린다. 로봇 몸체 띠와 접시가 이어진 덩어리는 박스 중심이 구역 안에 떨어지기도 한다.
  - 그렇게 버린 큰 덩어리에 블록이 붙어 있으면(구역 안 조각이 블록 최소 크기 이상), 그 조각만 `zone` 표시 박스로 남겨 검수로 보낸다. 구역 경계에서 잘린 박스이니 검수 때 크기를 맞춘다. 블록 최소 크기보다 가는 조각은 구역을 손으로 찍은 오차로 보고 버린다.
  - 구역 둘레 40px(`zone_margin_px`) 밖의 색 픽셀은 덩어리를 찾기 전에 지운다.
  - 버린 수는 실행 끝에 `⚠ 구역 밖 블록 후보 N개를 버렸다(사진 M장)` 로 나오고, 초안의 사진마다 `outside` 로 남는다. 버렸다는 것만으로는 사진이 검수로 가지 않는다.
  - ⚠ 구역 밖에 진짜 블록이 있으면 같이 버려져, 학습에서 그 블록이 배경으로 들어간다. 블록은 구역 안에 둔다.
  - ⚠ 구역을 찍을 때 로봇 몸체·접시를 덮지 않는다. 덮은 부분은 버리지 못하고 `큰 색 영역` 검수가 된다.
- 표시(`split` `defect?` `hand?` `edge` `small` `irregular` `zone`)가 하나라도 붙은 사진은 `review`(검수 필요)가 되고, 검수에서 통과하기 전에는 데이터셋에 들어가지 않는다. 표시가 없는 사진은 `auto` 로 바로 들어간다.
- 맞닿은 블록을 나누는 k-means 는 시작점을 고정했다. 같은 사진은 다시 돌려도 같은 박스가 나온다.
- 흰 매직블럭(예비)은 분홍·초록 색 규칙에 안 잡힌다. 흰 블록으로 바꾸게 되면 규칙을 다시 만들어야 한다.
- 같은 이름으로 다시 돌리면 검수한 초안을 `draft.json.bak-<시각>` 으로 백업한 뒤 새로 만든다.
- 내보내기는 사진 이름의 해시로 약 20% 를 valid 로 나눈다. 다시 내보내도 같은 사진은 같은 쪽에 간다.

### 실물 첫 10장으로 임계값 맞추기 (`--calibrate`)

1. 노출·WB·60Hz 를 고정하고 `zones.json` 을 찍은 뒤, 보정용 10장을 따로 찍는다(`capture.py --out vision/data/raw/calib`). 10장에 넣을 것:
   - 분홍·초록의 정상·불량이 모두 나오게(불량 블록은 X 가 보이는 면이 위로)
   - 맞닿은 블록 1~2쌍
   - 그릇 안의 블록
   - 손 2~3장
   - 블록 위치는 화면 가운데·가장자리 고루(가장자리는 옆면이 보인다)
2. `autolabel.py vision/data/raw/calib --name calib --marker <색>` → `review.py calib` 에서 10장을 모두 바르게 고쳐 **통과(P)**.
3. `autolabel.py --calibrate calib --marker <색>` 을 실행한다. 통과한 박스를 정답으로 보고 다음 값을 계산해 `vision/autolabel.json` 에 쓴다(이전 것은 `.bak-<시각>`). 이후 autolabel 이 자동으로 읽는다.
   - 블록 색의 HSV 범위.
     - 색상은 블록 픽셀 98% 가 가장 좁게 모인 구간 ± 5 다(10-22, 예전 1~99 백분위).
     - 채도 하한은 블록 채도 하위 2% − 15(최소 20)다.
     - 구역 안 배경이 그 규칙에 0.5% 넘게 걸리면 먼저 색상 구간을 95·90·85·80% 로 좁혀 본다. 그래도 걸리면 채도 하한을 그 배경보다 높게 올린다.
   - 불량 기준(정상 블록 최대 마커 비율과 불량 블록 최소 비율의 중간)
   - 블록 하나가 보이는 면적(`obj_area_px`)과 최소 크기. 최소 크기는 면적 하위 5% 로 잰다(가장 작은 박스 하나로 재면 반쯤 가려진 블록 하나 때문에 6px 까지 내려간다).
   - 블록 모양 기준(`shape`, 10-22): 새 색 규칙으로 덩어리를 다시 찾아, 검수 박스 하나에만 맞는 덩어리의 볼록도·가로세로비로 잰다. 합성 기본값보다 엄하게는 바꾸지 않는다. 맞는 덩어리가 8개 미만이면 그대로 둔다.
   - 손 최소 면적

   - 블록 영역은 박스 안에서 박스 둘레 배경과 색(Lab 의 a·b, 밝기 제외)이 다른 픽셀의 볼록 껍질로 잡는다. 회전한 블록은 박스 모서리가 작업대라서 박스를 그대로 쓰면 안 된다.
   - **10-22 에 바꿨다.** 예전에는 "배경보다 채도가 높은 픽셀"을 블록으로 봤다. 그런데 4600K 실물은 식탁보 채도(약 56)가 파스텔 블록(분홍 약 45)보다 높아서, 블록 픽셀이 하나도 안 나왔다(위 "구역 밖 버리기·보정 시험").
   - 블록 둘레 배경은 둘레 픽셀 중 **사진 전체 배경색(식탁보)에 가까운 것만** 쓴다(10-22). 녹화 사진에서 투입 구역 가장자리 블록은 둘레 절반 이상이 주황 테이프라, 기준이 테이프 색이 되고 문턱이 70 대로 뛰어 블록 픽셀을 하나도 못 찾았다. 둘레에 식탁보가 거의 없으면(그릇 안) 둘레 전체를 쓴다.
   - 채도 하한을 정하는 배경 통계는 `zones.json` **구역 안**에서만 잰다. 구역 밖 로봇 몸체·접시(초록 기운의 흰색)는 autolabel 이 어차피 버린다. 거기에 맞춰 채도 하한을 올리면 블록을 놓친다. 10-22 아침에는 구역 둘레 40px 까지 넣었는데, 아래쪽 구역 옆 로봇 흰 부품(H80 S49)이 걸려 초록 하한이 89 까지 올라갔다. 초안에 구역 경로가 없으면 `vision/zones.json` 을 쓴다.
   - **안전장치(10-22)**: 새 값과 지금 값으로 검수한 사진을 각각 다시 라벨해 비교한다. 새 값의 블록 F1 이 지금 값보다 0.02 넘게 낮으면 `autolabel.json` 을 바꾸지 않고 `autolabel.rejected.json` 에 남긴다.
4. 출력 끝의 "새 값으로 다시 라벨 vs 검수 결과" 표에서 `블록` 줄의 재현율이 0.95 이상이면 다음으로 넘어간다. ⚠ 경고가 나오면 3단계를 다시 한다. 경고의 뜻:
   - "정상 블록 최대 ≥ 불량 블록 최소" = 마커로 정상과 불량이 안 갈린다 → X 를 더 굵게 칠하거나 그 블록 사진을 확인한다
   - "구역 안 배경의 x% 가 이 색 범위에 걸려 채도 하한을 올렸다 — 블록을 놓친다" = 식탁보·그릇이 블록 색으로 찍힌다(배경 오검출 주의) → 색온도·조명을 고치고 1단계부터
   - "박스 안에 색 픽셀이 거의 없음" = 검수 때 박스를 잘못 그렸다
   - "새 값이 검수한 사진을 지금 값보다 못 맞춘다 … rejected.json 에 남겼다" = 보정을 쓰지 않았다. 검수 박스(블록마다 하나, 맞닿은 블록도 따로, 손은 손만)를 확인하고 다시 한다. 그대로 두면 기본값으로 라벨한다
- 카메라 높이나 각도를 바꾸면 블록 크기가 달라지므로 보정을 다시 한다.
- `--config <경로>` 를 주면 그 파일에 쓴다(시험용). 기본은 `vision/autolabel.json` 이다.

### 학습 메모

- 결과는 `vision/models/ball_int8_openvino_model` (+ `train_summary.json`)이다. 이 폴더가 생기면 detect.py 가 COCO 대신 이것을 쓴다.
- 학습 기록은 `vision/runs_train/ball_<시각>/` 에 남는다. 이름에 시각이 붙어 `-2` `-3` 같은 번호 폴더는 생기지 않는다.
- 같은 이름의 모델 폴더가 이미 있으면 지우지 않고 `models/_old/` 로 옮긴다. `--name` 을 주면 다른 이름으로 만든다(10-21 밤 시험 모델은 `e2e`).
- ⚠ **젠북 xpu 로 학습할 때는 먼저 OVMS 를 내리고(`systemctl --user stop ball-ovms`), 끝나면 다시 올린다(`./start_ovms.sh`).** LLM 두 개를 동시에 적재했을 때 GPU 가 멈춘 이력이 있고, 10-21 밤 OVMS 가 떠 있는 채로 학습했을 때도 OVMS 가 GPU HANG 으로 죽었다. GPU 를 나눠 쓰지 않는다. 학습 = 젠북 Arc GPU(xpu), 채점(검증) = CPU.
- ⚠ **에포크마다 하는 검증은 기본으로 끈다.** xpu 에서 검증하면 `NMS time limit exceeded` 로 후보가 잘려 점수가 가짜로 낮게 나온다.
  - 10-21 합성 데이터 실측: xpu 검증 P 0.931 / R 0.091 / mAP50 0.091, 같은 best.pt 를 CPU 로 검증하면 0.981 / 1.0 / 0.995.
  - 잘린 점수로는 best.pt 선택도 흔들린다. 그래서 학습이 끝난 뒤 CPU 로 한 번 검증하고 그 점수를 `train_summary.json` 에 적는다(로그의 `검증:` 줄).
  - 학습 로그 끝에 찍히는 마지막 에포크 점수는 xpu 검증이라 무시한다.
- 검증 사진이 적으면 재현율이 1/n 단위로 끊긴다. 150장이면 valid 가 20~30장쯤 된다.
- 커스텀 모델은 COCO 80종을 잊는다(교체이지 추가가 아니다). 손을 찾으려면 hand 를 라벨해야 하고, 그래서 검수 때 손을 그린다.

### Roboflow (대안)

자동 라벨 대신 Roboflow 로 라벨할 때: `autolabel.py ... --zip` 또는 검수 화면의 "zip 도" 로 만든 zip 을 업로드해 초안으로 쓰거나, 처음부터 라벨한 뒤 "YOLOv8" 형식으로 export → `$TPY vision/train.py --zip <파일>.zip`.

- **"YOLOv8" export 는 모델이 아니라 데이터셋이다**(jpg + 라벨 txt + data.yaml, `.pt` 없음). 모델은 `train.py` 가 만든다.
- **클래스 이름은 정확히** `red_ok` `blue_ok` `red_defect` `blue_defect` `hand` 로 쓴다. 다르면 `train.py` 가 멈춘다. Roboflow 는 클래스 번호를 알파벳순으로 매기지만, detect.py 는 번호가 아니라 모델에 들어 있는 이름으로 세므로 순서는 상관없다.
- **Preprocessing 의 Resize(기본 "Stretch to 640x640")는 끈다.** 켜 두면 640x480 사진이 세로로 늘어나 블록이 찌그러진 모양으로 학습된다. 추론은 비율을 유지한 레터박스라서 학습과 모양이 어긋난다.
- **Augmentation 의 Hue·Grayscale 은 쓰지 않는다.** 분홍과 초록의 구분이 흐려진다. Ultralytics 도 학습 중에 자체 증강(mosaic, 약한 HSV)을 한다.
- `data.yaml` 의 `train: ../train/images` 는 한 단계 위를 가리킨다. `train.py` 가 절대경로로 고친 `data_fixed.yaml` 을 따로 만들고 원본은 그대로 둔다(`--dir` 도 같다).
- 라벨 txt 는 마지막 줄 끝에 줄바꿈이 없다. `cat *.txt | wc -l` 로 세면 적게 나온다. `train.py` 가 분할별·클래스별 박스 수를 제대로 세서 출력한다.

## detect_objects()

```python
from vision.detect import detect_objects
r = detect_objects()                    # 위 카메라 한 장 (auto: 장치 또는 Studio 스트림)
r = detect_objects("some.jpg")          # 사진으로
```

- 반환값은 계약서 3절의 키(`ts` `zones` `hand` `objects` `image_path` `device` `latency_ms`)다. 참고값으로 `speed_ms` `capture_ms` `total_ms` `source` `model` `detections` 도 붙인다.
- `objects`(10-21 밤 추가): 블록 하나당 하나. 블록이 없으면 빈 목록이고, 손은 넣지 않는다.

  ```json
  {"cls": "red_ok", "zone": "input", "cell": "왼쪽 위", "px": [412, 233], "conf": 0.93}
  ```

  - `zone`: 블록 박스 중심이 든 구역이다. 5구역(`input` `bowl_red` `bowl_blue` `bowl_defect` `hand_spot`)을 이 순서로 보고, 어디에도 없으면 `"outside"` 다. 손에 놓인 블록은 `hand_spot` 이 된다.
  - `zones` 개수는 지금처럼 input·bowl_* 4구역만 센다. hand_spot·outside 블록은 `objects` 에만 있다.
  - `cell`: 그 구역 다각형의 바깥 사각형을 카메라 화면 기준 3×3 으로 나눈 칸이다. `outside` 면 화면 전체를 3×3 으로 나눈다. 이름 9개는 정확히 이것이다:

    | | 왼쪽 열 | 가운데 열 | 오른쪽 열 |
    |---|---|---|---|
    | 위 행 | `왼쪽 위` | `가운데 위` | `오른쪽 위` |
    | 가운데 행 | `왼쪽 가운데` | `가운데` | `오른쪽 가운데` |
    | 아래 행 | `왼쪽 아래` | `가운데 아래` | `오른쪽 아래` |

  - `px`: 위 카메라 픽셀의 박스 중심 `[x, y]`(정수)다. `conf` 는 검출 점수다.
  - 순서는 YOLO 출력 순서(점수 높은 순)다.
- 박스 사진의 글자는 OpenCV 글꼴이 한글을 못 써서 영어다: `pink` `pink X`(불량) `green` `green X` `hand`. 박스 색도 분홍·초록이다.
- `latency_ms` 는 Ultralytics 의 전처리+추론+후처리 합이다. 사진을 찍는 시간은 `capture_ms`, 호출 전체는 `total_ms` 다.
- 구역 판정은 박스 중심점으로 한다. 블록 4클래스는 input·bowl_* 구역에서만 센다. `hand.present` 는 hand 박스의 중심이 `hand_spot` 안에 있을 때만 true 다.
- 신뢰도 문턱은 구역별이다(10-23). 값은 `detect.py` 맨 위 `CONF_DEFAULT`(0.4)·`CONF_BY_ZONE`(그릇 3개 0.25) 한 곳에 있다. 가장 낮은 값으로 한 번 추론하고, 블록 박스 중심이 든 구역의 문턱으로 거른다.
  - 투입 구역·손 자리·구역 밖·손 박스는 0.4 그대로다. NMS 는 점수 높은 박스부터 고르므로, 0.25 로 받아 0.4 로 거르면 예전 0.4 결과와 같다(원본 156장에서 같음 확인).
  - 0.4 아래 박스가 이미 받은 박스와 IoU 0.5(`DUP_IOU`) 이상 겹치면 같은 블록으로 보고 버린다. NMS(IoU 0.7)를 지난 같은 블록 겹박스가 0.25~0.4 에 있기 때문이다.
  - `detect_objects(conf=0.4)` 처럼 값을 주면 모든 구역에 그 값 하나를 쓴다(예전 방식, 비교 시험용). 겹박스 거르기도 하지 않는다.
- `device` 는 OpenVINO 가 실제로 컴파일한 장치다(`EXECUTION_DEVICES`). Ultralytics 는 없는 장치를 받으면 조용히 AUTO 로 바꾸기 때문에, 요청한 장치가 아니라 실제 장치를 적는다.
- 모델은 프로세스당 한 번 읽고 컴파일한다.
- NPU 컴파일 결과는 `vision/.ov_cache` 에 캐시한다. Ultralytics 에는 이 옵션이 없어서 `ov.Core` 를 감싸 `CACHE_DIR` 을 넣는다(`enable_ov_cache()`). 그래서 새 프로세스의 첫 호출도 컴파일을 다시 하지 않는다. 모델을 바꾸면 캐시 키가 달라져 자동으로 다시 컴파일한다.
- 모델 선택 순서:
  1. `model=` 인자 또는 환경변수 `BALL_VISION_MODEL`
  2. `models/ball_int8_openvino_model`
  3. `models/coco_int8_openvino_model`
- COCO 모델로 검증할 때만 `COCO_ALIASES`(person→hand, sports ball→red_ok …)로 이름을 바꿔 센다. 블록 모델은 클래스 이름이 곧 계약 키다.
- 박스 사진 기본 위치는 `runs/<YYYYMMDD>/snap_<시각>.jpg` 다. `out_dir=` 로 바꿀 수 있다.
- `zones.json` 이 없으면 `FileNotFoundError` 를 낸다(먼저 zones.py).

| INT8 | CPU | 290 | 12.74 | 16.21 | 73.7 | 110.0 | 19.13 |
| INT8 | GPU | 2,678 | 3.31 | 3.66 | 289.7 | 454.0 | 9.0 |
| INT8 | NPU | 1,047 | 7.05 | 7.23 | 141.2 | 163.8 | 10.32 |
| FP16 | CPU | 119 | 27.49 | 35.37 | 34.5 | 33.2 | 34.12 |
| FP16 | GPU | 209 | 4.47 | 4.57 | 225.4 | 217.6 | 11.31 |
| FP16 | NPU | 660 | 7.81 | 8.17 | 126.8 | 145.3 | 10.84 |

읽는 법:
- **순수 추론 속도는 GPU 가 가장 빠르다.** NPU 는 CPU 보다 1.8배 빠르다(INT8 지연 기준).
- 이 프로젝트에서 비전을 NPU 에 두는 이유는 속도가 아니라 자리다. GPU 는 OVMS 의 LLM(Qwen3, `pull_models.sh` 에서 GPU 지정)이 쓰므로, 비전을 NPU 에 두면 GPU 를 비워 둘 수 있다.
- INT8 이 FP16 보다 빠른 정도는 장치마다 다르다: CPU 2.2배, GPU 1.35배, NPU 1.1배.
- e2e 는 Ultralytics 전처리+추론+후처리를 연달아 돌린 평균이다. `detect_objects` 는 호출 사이에 촬영(0.7초)이 끼어 NPU 가 쉬므로, 같은 NPU 라도 추론 시간이 15~16ms 로 더 길게 나온다.
- 측정할 때 OVMS 가 꺼져 있었다. OVMS 가 GPU 에서 LLM 을 돌리는 중이면 GPU 숫자는 달라진다.
- 블록 모델로 다시 잴 때: `$PY vision/bench.py` (`models/ball_int8_openvino_model` 이 있으면 자동으로 그것을 잰다)

조정 기준:
- 마지막 줄은 노출 점검이다. 흰 식탁보 위 화면 가운데에 분홍·초록 블록 몇 개를 두고 찍는다(구역을 찍기 전이라 화면 가운데 절반을 식탁보로 본다).

### 4. 학습용 140장 촬영 (25~30분)

```
$PY vision/capture.py --out vision/data/raw/$DAY
cp vision/data/raw/calib/*.jpg vision/data/raw/$DAY/
```

- 첫 줄은 창 모드다. 배치를 바꾸고 스페이스를 누른다.
- 간격 모드도 있다: `$PY vision/capture.py --out vision/data/raw/$DAY --interval 3 --count 50`. 3초마다 한 장 찍히니 그 사이에 배치를 계속 바꾼다.
- 둘째 줄: 보정 10장도 학습에 넣는다.

| 장면 | 장수 |
|---|---:|
| input 에 섞인 블록(3~20개, 맞닿은 블록·불량 포함) | 60 |
| 그릇 안에 블록이 있는 장면(옮긴 뒤의 모습) | 30 |
| hand_spot 에 손(펼친 손, 블록을 든 손) | 35 |
| 빈 작업대, 블록 1~2개 | 15 |

블록 섞기:
- 장면마다 블록을 손에 모아 흔들어 다시 놓는다. 위로 오는 면과 회전 각도가 매번 바뀌게 한다. 블록은 아무 면이나 위로 오므로, 학습에 여러 면·각도가 고루 들어가야 한다.
- 불량 블록은 6면 전부 X 를 칠했으니 어느 면이 위로 와도 X 가 보여야 한다. 촬영 전에 불량 4개를 한 번씩 굴려 6면을 확인한다. 흐린 면은 덧칠한다.
- 블록 위치는 화면 가운데와 가장자리에 고루 둔다. 가장자리에서는 옆면이 보여 모양이 달라진다.

맞닿은 블록:
- 장면의 2/3 쯤은 블록 사이를 손가락 한 마디(1~2cm) 띄운다. 맞닿은 블록 덩어리는 자동 라벨이 나눠 보고 `split` 표시로 검수에 보낸다(합성 시험: 몰아 쏟은 장면은 검수 사진이 흩어 놓은 장면의 9~20배).
- 나머지 1/3 은 일부러 맞닿게 둔다. 시연 때 투입구에서 블록이 붙어 있어도 하나씩 세어야 하므로 학습에 필요하다.

색:
- 블록은 분홍 8 + 초록 8 + 불량 분홍 2 + 불량 초록 2 를 다 쓰고, 장면마다 섞는다. 한 장에 분홍·초록이 같이 나오는 사진이 대부분이어야 한다.
- 흰 식탁보 위에 다른 분홍·초록·살구색 물건(포장지, 펜, 수세미 조각)을 두지 않는다. 파스텔은 채도가 낮아 비슷한 색을 블록으로 본다.
- 식탁보 주름·그림자는 펴 둔다. 그늘진 곳은 채도가 더 떨어진다.

그 밖에:
- 시연 때 로봇 팔이 시작 자세에서 화면에 보이면, 팔을 그 자세로 둔 채 찍는다.
- 조명과 카메라 값은 1단계 그대로 둔다. 바꾸면 3단계 보정을 다시 한다.
- 흰 매직블럭(예비)은 찍지 않는다. 색 규칙에 안 잡힌다.

```

```

브라우저로 `http://127.0.0.1:8791` 을 열고 아래 순서로 본다. 조작표는 위 "review.py 조작" 절에 있다.

1. 보기 "검수 필요": 노란 점선 박스를 고치거나 Enter 로 승인한다.
   - `split` 은 맞닿은 블록을 나눈 박스다. 블록 하나에 박스 하나가 맞는지 본다.
   - 손이 보이면 5(손) 상태에서 손목까지 드래그한다.

### 7. 학습 (약 11~12분)

```
systemctl --user stop ball-ovms
$TPY vision/train.py --dir vision/datasets/auto_day1 --fp16
./start_ovms.sh && sleep 15 && curl -s http://127.0.0.1:8100/v3/models
```

- **학습 전에 OVMS 를 내리고 끝나면 다시 올린다.** xpu 학습과 OVMS(LLM)가 GPU 를 같이 쓰면 GPU 가 멈춘다(10-21 오후 LLM 두 개 동시 적재 때 2회, 10-21 밤 이 학습과 겹쳤을 때 1회 → OVMS SEGV). GPU 를 나눠 쓰지 않는다. 학습 = 젠북 Arc GPU(xpu), 채점 = CPU.
- 학습 시간은 10-21 밤 합성 150장 실측(학습 9.7분 + 검증·export 0.4분)이다. `--fp16` export 가 약 10초 더 걸린다. OVMS 를 다시 올리는 데 7~14초 걸린다.
- 학습 중에는 에이전트·UI 의 말하기(STT)·LLM 이 안 된다. 녹화·시연 리허설과 시간을 겹치지 않는다.

- 출력 끝의 `검증:` 줄(CPU 검증)과 `[export int8]` 줄의 `npu_compile_ms` 를 본다.
- 결과는 `vision/models/ball_int8_openvino_model` 이다. 이 폴더가 생기면 detect.py 가 COCO 대신 이것을 쓴다.
- `--fp16` 은 bench 비교용 FP16 모델이다. 빼면 export 시간이 줄어든다.

### 8. NPU 검출 확인·bench (5분)

```

$PY vision/bench.py
```

- 첫 줄 JSON 에서 볼 것:
  - `zones` 의 개수가 작업대 실제와 같은지
  - `objects` 의 블록마다 `zone`·`cell` 이 실제 놓인 자리와 맞는지
  - `device` 가 `NPU` 인지
  - `latency_ms`(두 번째 호출부터 컴파일 없음)
- 둘째 줄: 박스 사진을 연다.
- 셋째 줄: 블록 모델로 장치별 숫자를 다시 잰다 → `vision/bench_results.md`.

### 방법 B — 녹화 영상에서 학습 사진 뽑기 (10-21 밤 검토)

ACT 녹화(4정책 × 50 에피소드)의 위 카메라 영상은 YOLO 학습 사진과 같은 카메라·자리·설정이다. 에피소드마다 첫 장면(블록이 놓인 채 팔이 홈)과 끝 장면(옮긴 뒤 팔이 홈)을 뽑으면 4단계 140장 촬영을 대부분 대신한다.

**판단**
- **대신할 수 있는 것: 4단계 140장 촬영.**
  - 장수: 중복을 빼고 약 300장이다(아래 표, 추정). 계획한 140장보다 많다.
  - 장면: 녹화 가이드 4절의 장면이 곧 시연 장면이다. 불량 섞인 11개, 분홍·초록 4+4, 그릇 안, 손 위 블록이 모두 들어 있다.
  - 팔 위치: 첫·끝 장면은 팔이 홈 자세라, detect 를 부르는 순간(정책이 끝나 팔이 홈)과 같다.
- **대신 못 하는 것 → 따로 한다.**
  1. 0~2단계(카메라 고정·노출 점검·구역)는 녹화 전에 그대로 한다. 구역이 있어야 가림 검사를 할 수 있다.
  2. 보정 10장은 따로 찍지 않는다. 첫 정책 녹화에서 뽑은 사진 10장으로 한다. 압축이 같은 사진으로 보정해야 검수가 덜 는다(아래 시험: 압축 안 된 사진으로 보정하면 18 → 40장).
  3. 직접 촬영 약 20장(capture.py, 10분)을 녹화 전에 찍는다.
     - 손 10장: B 말고 다른 사람의 손, 손바닥 방향·위치를 바꿔서. 녹화에는 B 의 펼친 손바닥 한 자세뿐이다.
     - 블록 섞은 장면 10장: 학습은 압축 영상으로, 추론(detect)은 압축 없는 카메라 사진으로 하므로 그 차이를 메운다.
- **단점: YOLO 사진이 녹화가 끝나야 생긴다.**
  - 손(hand) 클래스는 handoff 녹화가 끝나야 학습할 수 있다. 그 전 모델은 `hand.present` 가 늘 false 다.
  - 그래서 진짜 비전으로 에이전트를 시험하는 일은 녹화 뒤로 밀린다.
  - 방법 A(아침에 140장)는 녹화 전에 모델이 나오지만, 촬영·검수에 약 1시간이 더 든다.

- Studio 의 데이터셋 API 는 요청을 동기로 처리한다.
- 그래서 **녹화 화면이 열려 있는 동안에는 뽑지 않는다.** 정책 하나를 끝내고 ← 로 나온 뒤에 돌린다.
- 영상 파일 확인은 한 번 실행에 파일당 1번만 한다. 응답이 없으면 10초 뒤 한 번 더 하고, 그래도 없으면 멈춘다.

**내일 순서 (방법 B)**

| 시점 | 할 일 | 시간 |
|---|---|---|
| 녹화 전 | 0~2단계 그대로(카메라·노출 점검·구역) + 직접 촬영 약 20장(손 10, 블록 섞은 장면 10) | 기존 + 10분 |
| `pick_defect` 녹화 끝 | 뽑기 → 자동 라벨 → 10장 검수·통과 → `--calibrate` → 다시 자동 라벨 → 나머지 검수 | 20~25분 |
| `pick_red` 녹화 끝 | 뽑기 → 자동 라벨(검수한 사진은 그대로) → 검수 → **1차 학습**(약 160장, 약 12분) → NPU 확인 | 약 35분 |
| `pick_blue` 녹화 끝 | 뽑기 → 자동 라벨 → 검수 | 약 10분 |
| `handoff` 녹화 끝 | 뽑기 → 자동 라벨 → 검수(손 박스 약 100장 그리기) → **2차 학습**(전부 약 330장, 약 25분, `--epochs 30` 이면 약 15분) → NPU 확인·bench | 약 60분 |

- **학습(xpu)은 Studio 가 녹화하는 동안 돌리지 않는다.** Studio 는 녹화 영상을 GPU 의 영상 압축기(QSV)로 압축하는 것으로 보인다(Studio 패치 파일 `streaming_encoding_settings.py` 주석). xpu 학습이 GPU 를 같이 쓰다가 멈춘 이력도 있다(10-21 밤 OVMS). 1차 학습은 점심 등 녹화를 쉬는 때에 OVMS 를 내리고 한다.
- 1차 모델에는 손이 없다(handoff 전). `hand.present` 시험은 2차 뒤에 한다.
- 방법 A 와 섞어도 된다. 녹화 전에 시간이 있으면 4단계를 40장쯤만 찍어 0차 모델로 파이프라인을 먼저 시험하고, 녹화 사진으로 1·2차를 한다.

**명령**

```
$PY vision/frames_from_dataset.py --list                                     # 데이터셋 이름·카메라 이름 확인
$PY vision/capture.py --out vision/data/raw/rec                              # 녹화 전 직접 촬영 20장(같은 폴더)

$PY vision/review.py rec                                                     # 나머지 검수 → 데이터셋 내보내기
# 다음 정책이 끝날 때마다: 뽑기(--out 같은 폴더) → autolabel(같은 이름) → review → 내보내기

```

- 손 장면이 더 필요하면 handoff 를 `--every 1` 로 한 번 더 뽑는다(같은 폴더, 중복은 자동으로 빠진다). 팔이 손 쪽으로 뻗은 장면이 들어가는데, detect 를 부를 때와는 팔 위치가 다르니 많이 넣지 않는다.
